## For the owner

- **Changes to the spec you are asked to approve.** Until you approve each one, the spec text stays as written and the contract wins for P4 only. Security won every trade-off.
  - Decision 4 (L827, L1322, L1341, L1483): `requireWalletOwner(proId)` is not built, in `client.ts` or anywhere: every export of a `"use server"` file is a public endpoint (an identity helper that returns a customer id must not be one), and a separate writer would let a wrapper link the account before its core has parsed and throttled the call. The Owner is the `owner` of the visitor `resolveVisitor` returns (read-only, `src/server/visitor.ts` `currentPublicVisitor`), and `bookWithHeldTicketCore` makes the one write itself; a pure guard fails if any source file names `requireWalletOwner`.
  - Decision 5 (L1344): the Owner is the customer whose e-mail is the session e-mail AND whose `user_id` is null or the session user (the spec names the e-mail only): a row already linked to another account is never treated as yours; the cards of `getMySpace` follow the same rule (`ownedCustomerRows`, G3a), a second change to the spec's L1377-1378: a row linked to the user under another address is neither a card nor an Owner.
  - Decision 6 (L791): `upsertCustomer` enforces in SQL, on insert and on conflict, that `user_id` is set only for a verified user with the same e-mail, and that a missing phone is filled only by that user (the spec left it to the caller): anonymous input can no longer link an account or fill a stranger's phone.
  - Decision 7 (L1369): « Réserver avec 1 ticket » for a visitor who holds only a personal-link cookie opens the code dialog with an EMPTY address field (the spec prefills it): the cookie can be planted by a cross-site navigation, and a prefilled or locked address would steer the victim onto the attacker's identity.
  - Decision 9 (L1445-1455): two states are added to the séance page: « En cours » (started, not ended) and « Réservations pas encore ouvertes » (beyond the effective horizon, reachable by URL only).
  - Decision 27 (L1145, L1870): the mock checkout is reachable only when Stripe is off AND outside production, by `APP_ENV` and by `VERCEL_ENV` (the spec cuts it once Stripe is active), and a Vercel production deployment refuses to boot when `APP_ENV` is not `production`: `APP_ENV` defaults to `development`, so a keyless production would hand out free tickets (SEC-I5).
  - Decision 28 (L1146-1147): the mock checkout GET shows a simulated page and writes nothing; its same-origin POST pays and answers 303 to `merci` (the spec redirects on the first call): no side effect on a GET (prefetchers, L1847), and the abandon flow is testable in mock mode.
  - Decision 32 (L1167-1168): « Libérer ma place » releases nothing when Stripe cannot be reached, nor when Stripe says paid or processing, nor when the booking is confirmed (the spec releases otherwise): releasing a session that may still be paid would turn a payment into a late payment.
  - Decision 40 (L1228-1235): the code dialog uses the sign-in code for signed-out visitors only, and verification codes are sent only for a session of the same address (the spec counts and sends them for any existing account): closes OUT:129 (enumeration by timing, confirmation mails pushed to strangers).
  - Decision 64 (L709, L822): for a visitor who is not a verified identity, no answer depends on another customer's state: a free registration that hits `already_booked` answers as a new address would on this séance (a fresh success, or the same « Complet » answer when no seat is left) and re-sends the confirmation of the existing booking to its address only; a buy + book that hits `already_booked` or `too_many_holds` answers one neutral sentence. A verified identity keeps the engine sentences.
  - Decision 65 (L1268-1273): seat holds and free registrations are bounded per séance, per pro and per IPv6 /48, and buy + book refuses a new hold on a séance that already carries `holdCeiling(capacity)` live holds. The IP and /48 keys carry no pro, so their reach is platform-wide (final review RND-2): see « Residuals accepted » and the owner check after go-live.
  - Decision 66 (L1268-1273): booking with a held ticket, client cancellation and « Libérer ma place » are throttled (`held`, `cancel`, `release`); the spec lists `free`, `buybook`, `rdv` and `shop` only.
  - Decision 67 (L1268-1273): e-mail keys are per pro (the spec's 6 per hour) plus a global mailbox bound (20 per hour), and a verified identity is throttled on its user key only: strangers typing an address can neither lock its verified holder out nor pin her holds.
  - Decision 68 (L1365-1366): a personal link sets the cookie only through a same-origin confirmation page (the spec sets it on the GET): a cross-site navigation or a mail scanner can no longer plant an identity.
  - Decision 69 (L1115-1117): every Checkout session carries `metadata { purchaseId, app: "skedul-tickets", env }`, and the webhook handles only its own app and environment (the spec records any paid session without a purchase as an orphan payment): the account also receives other billing, Payment Links and the events of other deployments, none of which is ever an orphan to refund.
  - Decision 72 (L1345-1346): the cross-pro link of `customer.user_id` at sign-in is removed (the spec links every pro's rows of a verified user): that link made the « Compte client lié » badge an oracle for typed addresses (FR:SEC-5). The link now comes only from the user's own act at that pro. This answers the SEC-5 question the P3 outcome left to you (« show it only when the link came from that client's own action at this pro »); it was applied without waiting because security comes first.
  - Decision 73 (a change to the P3 contract, not to the spec): the pro's client search goes through a Server Action and keeps the term in component state; `?filter=` stays in the URL (FR:UI-13). Cost: a search result has no shareable URL.
  - Decision 76 (L285, stricter; the P4 final review, PAY-3): a paid offer costs at least the Stripe minimum charge of the pro's currency, 0,50 € for EUR (the spec asks `price_cents > 0` only): the back-office refuses less on create and update, refuses to put an older offer under it back en vente, and the offer dialog checks it before the call; the DB CHECK stays `> 0`, no migration. Stripe refuses a Checkout under its minimum, so such an offer could be listed but never bought. Cost: no offer under 0,50 €.
